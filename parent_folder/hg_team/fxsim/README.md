# fxsim: WLED effects running in the browser

WLED's 1D effects, ported from `wled00/FX.cpp` to JavaScript, so a page can show an animated preview of an effect in its
real colours **before** it's applied to the strip. Built by wled-main-6c (lead) with 7 subagents on 2026-09-29.
AI-generated: every file carries `// AI: below section was generated by an AI` / `// AI: end` markers.

Used by: wled-main-2a's virtual device (`hg_team\virtualdev`: strip rendering and `/home/fx.js`) and the `/home` page previews.

## API in short (details in `src/SPEC.md`)

```js
FXS.setPalettes(palx.p);                 // once per /json/palx?page=N response
const h = FXS.preview(canvas, {fx: "Breathe", sx: 128, ix: 128, pal: 11, col: [0xFF0000, 0, 0], bri: 200, len: 60});
h.set({sx: 200});                        // slider change keeps state; a new fx or len restarts the effect
h.pause(); h.resume(); h.stop();
FXS.has("Image")                         // false: not ported, the preview is the fallback palette scroll
// Node / virtual device: const seg = FXS.makeSeg(o); FXS.step(seg) every 23 ms; seg.S.px = Uint32Array 0xWWRRGGBB
```
Display rule, the same as 2a's real `/home/ws` stream: shown = colour × (bri/255)^(1/2.2); W is added onto RGB.
The preview clock starts at 10 min "uptime" (`o.t0`). `o.rate` fast-forwards slow effects (not device-faithful for effects that count frames).

For comparison: the `/home` page is about 24-26 KB gzip, and the firmware has about 230 KB flash free (board section 5).
Packaging options (decision for the user and ad):
- **Firmware PROGMEM:** always there, costs flash.
- **Optional LittleFS file `/fxsim.js.gz`:** zero flash, and can be updated by re-uploading. WLED's `handleFileRead` serves `path.gz`, see `wled00/file.cpp:478-498`. The page must **not** load it while `cfg.pinSet === false` (X22: without a settings PIN anyone can upload files).

## Accuracy

| Status | Effects |
|---|---|
| **Ported 1:1 from the C code** | 146 of the 148 1D effects: every effect that isn't 2D-only |
| Not ported (fallback preview) | Copy Segment (needs another segment), Image (needs a GIF file) |
| Out of scope | 53 effects that are 2D-only |

**Verified bit-exact** against an independent Python transliteration of the C code: 151 of 151 groups. That covers sin8/16, beat8/16/88,
beatsin*, color_blend/add/fade, hsv2rgb, rgb2hsv, perlin8/16 (1-3D), sqrt32_bw, the PRNG, and all 67 palettes via ColorFromPalette
with 3 blend types. `check.js`: 146/146 pass (no exceptions, integer colours, uint16 aux0/aux1, animation, speed; the slowest effect takes 0.036 ms/frame at 150 LEDs).

**Where a preview differs from the device:**
- **Random numbers:** a seeded PRNG replaces the hardware RNG, so the character is the same but not the exact sequence.
- **Music effects (24):** driven by a synthetic 120 BPM song (kick, hi-hat, snare). The real strip reacts to real sound, so the preview shows the effect's character, not what your music will look like.
- **One plain segment:** no transitions, grouping, spacing, mirror or reverse. The fixed ESP32 limits (sparks, ripples) are the no-PSRAM values.
- **Palette 1** (random cycle) is approximated. Some effects keep C floats as doubles (sub-LSB differences).
- **C quirks are reproduced on purpose**, so the preview matches the device. See "Core WLED bugs found" below.
- **Faithful but they look static in a short preview:** Sunrise (runs for minutes), Slow Transition, Spots, Solid Pattern(s), Traffic Light (a 12.8 s phase at speed 128), Midnight (brightness 15%).

## Core WLED bugs found while porting (`[code]`, verified by wled-main-6c and 30; routed to 84; all low severity)

1. `FX.cpp:1400` gradient_base: `1 + loading ? ix/2 : ix/4` parses as `(1+loading) ? …`, so Gradient's border is always intensity/2.
2. `FX.cpp:1355` mode_rain: `if (aux1 == 0) aux0 = UINT16_MAX` is a copy-paste typo (it should set aux1).
3. `FX.cpp:1257` Scanner Dual sets `SEGMENT.check1 = true` and never restores it (Dynamic Smooth at `:422-424` does restore), so "Dual" stays ticked after switching back to Scanner.
4. `colors.cpp` color_add, non-preserveCR branch: the saturation ORs 0xFF into an overflowed channel but never clears its 9th bit. That bit leaks into
   the next channel's lowest bit (red+red = `0x01FF0000`, a stray 1/255 on W; blue overflow → G+1; green overflow → R+1). The comment's example
   `0x01EF01EF | 0x00FF00FF = 0x00FF00FF` is wrong (it's 0x01FF01FF). Fix: `rb = (rb | sat) & 0x00FF00FF` (and the same for wg). Visually negligible.
